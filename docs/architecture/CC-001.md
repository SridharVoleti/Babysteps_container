# CC-001 — Consumer App Container Responsibility Boundary

Status: APPROVED / FROZEN

## Invariant

Babysteps Platform is the authority. The Consumer App Container is the reusable common runtime. A learning app owns only educationally unique curriculum/content, learning logic, app-specific interactions, and app-specific presentation.

Learning apps must not bypass or independently implement platform-owned or container-owned capabilities.

## Allowed dependency direction

`apps/<app> -> src/container/public -> container-owned integration -> approved Babysteps platform contracts`

App packages must not depend on `src/container/internal`, direct database/Supabase clients, platform-private endpoints, auth internals, billing internals, or private platform implementation details.

## Unsupported app needs

When an app needs functionality that the current public contract does not expose:

1. Classify the need as either app-specific or reusable/common container capability.
2. If app-specific, use an already approved extension mechanism.
3. If reusable/common, propose a new container capability or extension point for explicit requirements/governance approval.
4. Do not copy, fork, monkey-patch, or privately import container core code as a workaround.

CC-004 defines the approved extension model in detail; CC-001 establishes the no-bypass/no-fork responsibility boundary.

## Enforcement

`npm run check:architecture` scans learning-app source code and fails on prohibited dependency/authority patterns. `npm run test:architecture` verifies the CC-001 rules. CI runs both for every push and pull request.

## Acceptance mapping

- CC-001-AC01: compliant public-container import fixture builds/tests.
- CC-001-AC02: private-container imports are rejected.
- CC-001-AC03: direct Supabase/platform-data access is rejected.
- CC-001-AC04: app-side platform authority decision implementations are rejected by architecture rules/review.
- CC-001-AC05: unsupported needs follow the governance path above; container forks are prohibited.
