# CC-002 — Standard App Manifest

Status: implemented against frozen acceptance criteria.

## Contract

Each learning app must provide a version-controlled `app.manifest.json` colocated with the app package. The manifest declares only app-specific differences. Platform-owned learner, entitlement, subscription, billing, session and other authoritative runtime state must never appear in it.

Required fields:

- `appId`
- `appVersion`
- `containerContractVersion`
- `contentVersion`
- `progressSchemaVersion`
- `requiredCapabilities`
- `entryPoint`

Convention/default fields:

- `contentConfiguration`: `{}`
- `optionalCapabilities`: `[]`
- `extensionPoints`: `[]`

The container validates and resolves the manifest before importing the app entry point. Required capability or compatibility failures block launch. Unsupported optional capabilities are removed from the resolved capability set and reported as degraded. Validation errors never include secret values.

## Stable errors

- `MANIFEST_INVALID`
- `MANIFEST_PROHIBITED_DATA`
- `CONTAINER_VERSION_UNSUPPORTED`
- `CAPABILITY_UNAVAILABLE`
- `ENTRY_POINT_INVALID`

## Acceptance mapping

- CC-002-AC01: valid minimal manifest resolves defaults and entry point may load.
- CC-002-AC02: malformed/missing required values fail before app code executes.
- CC-002-AC03: unsupported container contract fails launch and CI.
- CC-002-AC04: unknown required capability blocks launch; unknown optional capability follows explicit degraded behavior.
- CC-002-AC05: secrets and platform-authoritative runtime data are rejected without value leakage.
- CC-002-AC06: resolution is deterministic and frozen for identical package/container inputs.

CI runs the same validator used by runtime resolution via `npm run check:manifests`.
